1.0 Automation Fundamentals Core concepts every automation builder needs first

Essential Vocabulary — Words You'll See Everywhere START HERE

Before anything else, a handful of words get used constantly throughout this entire masterclass — in every tool, every lesson — without always being spelled out. Learn these seven first, and nothing later will feel like it's assuming knowledge you don't have.

API (Application Programming Interface)

You've been reading the word "API" since the very first lesson. Here's the formal definition: an API is simply the set of rules an app publishes for how OTHER programs are allowed to talk to it. Every GET, POST, webhook, and API key you've learned about is really just one piece of "using an API."
It's a restaurant menu — you don't walk into the kitchen and cook it yourself, you place orders using the exact options they've listed. An API is that same idea for software: a fixed menu of things you're allowed to ask for.
Ang API ay parang menu sa restaurant — hindi ka pumapasok sa kusina para magluto, sinusundan mo lang ang listahan ng pwedeng hilingin. Ganito rin sa software: ang API ang listahan ng mga bagay na pwede mong hingin sa isang app.
Every lesson from here forward — GET requests, webhooks, status codes, credentials — is really just "how to use an API," broken into individual pieces. If anything ever feels disconnected, it's still all just this one idea.

CRM (Customer Relationship Management)

A CRM is software built to track every person your business talks to — contact info, past conversations, what stage they're at in your sales process — in one place instead of scattered across emails, spreadsheets, and sticky notes.
It's a shared, permanent memory for your whole team — instead of one salesperson keeping details in their own head, everyone can look up the exact same history for any customer, any time.
Ang CRM ay parang alaala ng buong negosyo — nandiyan lahat ng detalye tungkol sa bawat customer, hindi lang nasa utak ng isang tao. Kahit sino sa team ang tumingin, makikita nila ang parehong impormasyon.
GHL calling itself a CRM is exactly why it also handles pipelines, tags, and contacts — those are the core building blocks of any CRM, automation aside.

No-Code vs. Low-Code

No-code means building something entirely through visual tools — dropdowns, drag-and-drop — without writing programming code. Low-code means mostly visual, with the option to drop into real code for the rare case the visual tools can't handle.
No-code is assembling furniture with just the included tool and instructions. Low-code is the same furniture kit, but you're allowed to grab a power drill from your own toolbox if a screw won't budge.
Ang No-code ay paggawa ng automation gamit lang ang dropdown at drag-and-drop — walang code na isusulat. Ang Low-code naman ay halos ganoon din, pero pwede kang gumamit ng totoong code kung talagang kailangan.
Zapier and GHL lean no-code. n8n and Make are low-code — visual first, with a Code node or module waiting in the wings for the rare moment you actually need it.

Self-Hosted vs. Cloud-Hosted

Cloud-hosted means the company runs the software on their own servers, and you just log in through a browser — zero setup, but you're relying on them. Self-hosted means you run the software on your own server or computer — more control and often cheaper, but you're responsible for keeping it running.
Cloud-hosted is renting an apartment — someone else handles the plumbing and the building. Self-hosted is owning a house — more freedom to do what you want, but you're the one who fixes it when something breaks.
Ang Cloud-hosted ay parang umuupa ng bahay — ang may-ari ang nag-aayos kung may masira. Ang Self-hosted naman ay parang sarili mong bahay — mas malaya ka, pero ikaw din ang mag-aayos kapag may problema.
This is exactly why n8n can be free — self-hosting shifts the server cost from n8n's pocket to yours, in exchange for you handling the upkeep.

Endpoint

An endpoint is the exact address a request gets sent to — a specific URL representing one particular thing you can ask an API to do, like /orders or /contacts. A webhook URL is one example of an endpoint.
If an API is the whole office building, an endpoint is one specific door with a department name on it — "Orders," "Contacts" — and you have to knock on the right door for what you need.
Ang Endpoint ay ang eksaktong address na pupuntahan ng request — parang partikular na pinto sa opisina, halimbawa "Orders" o "Contacts." Kailangan mong kumatok sa tamang pinto para sa kailangan mo.
When an HTTP Request node asks for a "URL," it's asking for the exact endpoint — get even one character wrong here and you'll see a 404, straight from the status codes lesson.

Sub-account (GHL)

In GHL, a Sub-account is one completely separate workspace — its own contacts, pipelines, and workflows — living inside one Agency account. An agency typically runs one sub-account per client.
It's a mall with one management office (the Agency account) and many separate stores inside it (sub-accounts) — each store runs its own business, but the mall owner can see and manage all of them.
Ang Sub-account ay parang hiwalay na tindahan sa loob ng isang malaking mall — sarili nitong customer, workflow, at setup, pero ang may-ari ng buong mall (Agency account) ay may access sa lahat ng tindahan.
This is exactly what makes Snapshots so powerful — build the perfect setup once, then deploy it as a fresh sub-account for every new client.

Instance

An instance is one specific running copy of a piece of software. "Your n8n instance" means the particular installation you're using, as opposed to n8n the software in general.
It's the difference between "a car" (the general idea) and "the car in your driveway" (one specific, actual copy of that idea) — the workflow you build lives on one specific instance, not on n8n as an abstract concept.
Ang Instance ay tumutukoy sa isang partikular na gumaganang kopya ng software — hindi lang basta "n8n" sa pangkalahatan, kundi ang eksaktong installation na ginagamit mo.
This is why exporting a workflow matters — moving it between instances (your test instance to your production instance, for example) is exactly what that JSON export file is for.

What is Automation? BEGINNER

The Simple Definition

Automation is making things work by themselves WITHOUT you manually doing them every single time.
Think of it like a coffee machine with a timer. Instead of you waking up and brewing coffee every morning, the machine does it automatically at 6 AM. You set it once, and it repeats forever.
Ang automation ay parang may robot na tumutulong sa iyo. Sinabi mo lang sa robot kung ano ang gagawin, tapos gagawa niya ng paulit-ulit nang hindi ka na kailangan mag-alala.

Real-World Examples

  • When you get a new email → automatically save attachment to cloud storage
  • When a customer buys something → automatically send them a thank you email
  • When a lead fills a form → automatically add to your CRM and send notification

Workflow ay tulad ng proseso sa pabrika. Ang input papunta sa step 1, tapos step 2, step 3, hanggang sa nakuha ang output. Walang tao na kailangan mag-decide sa bawat hakbang.

2.0 Web & API Fundamentals The request/response layer underneath every automation tool

Before n8n: How Two Apps Actually Talk STEP 1

Every automation tool you'll ever touch — n8n, Zapier, Make, all of them — is really just a nice-looking wrapper around one simple thing: two computers having a conversation. One side asks for something or hands something over, and that's called a request. The other side answers, and that's called a response. That's the entire foundation. Everything else you'll learn is just detail on top of that one idea.

The two-way conversation every single automation step is built on
It's exactly like calling a restaurant. You (the client) ask for a large pepperoni pizza — that's your request. The restaurant (the server) doesn't guess; it confirms the order and tells you when it'll be ready — that's the response. If they're out of pepperoni, they tell you that too. That "sorry, can't do that" reply is what you'll later recognize as an error message.
Kapag nag-uusap ang dalawang app, parang tumatawag ka lang sa isang tao. Ikaw ang nagtatanong o nagbibigay ng impormasyon (request), at sila ang sumasagot (response). Yun lang talaga ang buong ideya sa likod ng bawat automation — lahat ng iba pa ay detalye na lang sa ibabaw nito.

GET, POST, and the Words on Every Node STEP 2

Every request has to say what it's asking for, and instead of writing a full sentence, computers agree on one short word for it. You'll see these four words constantly, on almost every "Action" step you ever configure, no matter which tool you're in.

The four verbs behind almost every "Operation" dropdown you'll ever see

GET is by far the most common one you'll run into — nearly every "check for new data" trigger is secretly making a GET request behind the scenes. POST, PUT, and DELETE are what your "Action" steps use once they need to actually create, change, or remove something in the other app.

GET ay parang paghingi ng impormasyon — "pakita mo sa akin." POST ay paggawa ng bago — "gumawa ka ng bago dito." PUT ay pagpalit sa laman ng isang bagay — "palitan mo ito." DELETE naman, tanggalin — "alisin mo ito." Apat na salita lang, pero yan na halos ang lahat ng ginagawa ng bawat Action step.
DELETE is almost always permanent — there's usually no undo button on the other end. Test any workflow with a DELETE step on throwaway data first, and double-check exactly which record's ID you're sending before it ever touches real data.

Why Everything Looks Like Curly Braces STEP 3

Once two apps agree to talk, they need a shared format for the information itself — and almost everyone uses something called JSON. It sounds technical, but it's really just a tidy way of writing information down as labeled pairs, the same way you'd fill out a form.

Same information, two ways of writing it down

You never have to memorize this syntax to use n8n, Zapier, or Make — the interface reads it for you and shows each piece as a labeled field or dropdown. But now, when you see an "Output" panel full of curly braces and colons, you'll recognize it for what it is: a very organized form, not code you need to write.

Ang JSON ay parang form na may label ang bawat blangko. Sa halip na nakasulat sa papel, nakasulat ito gamit ang curly braces at colon. Hindi mo kailangang bumasa ito parang code — basahin mo lang parang form: pangalan ng field, tapos ang laman nito.

Webhooks vs. Checking Every Few Minutes STEP 4

Here's the question that trips up almost everyone starting out: how does an automation know the instant something happens? There are only two ways to do it, and once you see them side by side, webhooks stop being mysterious.

Same goal — "know when something happens" — two very different amounts of effort

Polling means your automation taps the other app on the shoulder over and over — "anything new? anything new?" — usually every few minutes, whether or not anything actually happened. It works almost everywhere, but it wastes effort and always runs a few minutes behind.

A webhook flips that around. Instead of you asking repeatedly, you hand the other app your address ahead of time, and it messages you the instant something happens — no asking required. That's why webhook-triggered workflows feel instant, while polling-triggered ones always lag a little.

Ang polling ay parang tumatawag ka paulit-ulit sa isang tao para itanong kung may bago na — kahit wala pa. Ang webhook naman, sila mismo ang tatawag sa'yo agad kapag may nangyari. Mas mabilis at mas hindi nakakapagod ang webhook, kaya mas gusto ito ng mga automation kapag available.
If an app gives you the choice, pick the webhook trigger over the "check every X minutes" one — it's faster for you and lighter on both apps.

What "Processing" the Data Actually Means STEP 5

"Processing" or "transforming" data sounds technical, but it just means reshaping information into whatever the next app needs — nothing more mysterious than that. A form might hand you a full name in one field, but the next app might want a first name and last name split apart. A transform step is the part of your workflow that splits, combines, renames, or cleans up fields so the next app can actually understand what it's receiving.

Same information, reshaped so the next app can actually use it

In n8n this happens inside an Edit Fields or Code node. In Zapier it's a Formatter step. In Make it's usually built right into the module itself. Different names, same job — translating between two apps that don't quite speak the same dialect.

Ang "processing" o "transforming" ay parang pag-aayos ng gulo. Kung magulo pa ang datos na dumating, inaayos muna ito bago ipasa sa susunod na app — parang nililinis mo ang mensahe bago mo ito ipadala sa iba.

How Your Automation Proves Who It Is STEP 6

A server won't just hand your emails or your spreadsheet data to anyone who politely asks — it needs proof that the request is actually allowed to be there. That proof is called authentication, and in n8n, Zapier, and Make you'll meet it under one name: Credentials. There are really only two common shapes it comes in.

Two ways to prove a request is allowed — a shared secret, or a one-time login that hands out a token

An API key is just a long secret string, like a spare house key — you paste it into the tool once, and every request quietly includes it to prove it's really you. OAuth is the flow behind every "Sign in with Google" button: instead of handing your actual password to n8n or Zapier, you approve access one time in a popup, and Google hands the automation a special token to use instead — so the tool never sees your real password at all.

This is exactly what's happening the first time you connect a new app in n8n or Zapier and it asks you to "authenticate" — you're either pasting in a key, or clicking through an OAuth login. Either way, after that first time, the tool remembers the credential and reuses it silently on every future request.
Ang API key ay parang susi na ibinibigay mo minsan lang, tapos gamit na gamit paulit-ulit. Ang OAuth naman ay parang pag-verify gamit ang Google o Slack — hindi mo ibinibigay ang password mo, pumapayag ka lang minsan, tapos bibigyan ka ng espesyal na pass na ginagamit paulit-ulit.
Treat an API key exactly like a password. Never paste one into a shared Slack message, a screenshot, or a public repository — anyone who gets hold of it can act as if they were you, with whatever access that key allows.

Reading the Status Code on Every Response STEP 7

Every single response carries a three-digit number called a status code, and it tells you — before you even look at the data — whether things went well. You don't need to memorize all of them; you just need to recognize which neighborhood a number lives in.

The first digit tells the whole story before you read another word

There's one more worth knowing by name: 429 Too Many Requests. It means you're calling the app faster than it allows — the fix is almost always to slow down or add a delay between calls, not to panic that something's broken. When a node fails in n8n or Zapier, the status code is usually the very first thing shown in the error, so this one number tells you where to start looking before you read anything else.

Kapag 2xx ang code, gumana — okay lahat. Kapag 4xx, may mali sa ginawa mo — baka mali ang API key o walang ganoong address. Kapag 5xx naman, hindi mo kasalanan — sila ang may problema sa server nila.
Retrying instantly and repeatedly after a 429 makes things worse, not better — some APIs will temporarily block your key entirely if you keep hammering them. Always wait before retrying (see the Retrying Without Hammering the Door lesson later in this tab).

When You Get More Than One Thing Back STEP 8

So far every example handed back one object — one order, one contact. But ask for "all orders from today" and you won't get one object back, you'll get a list of them. That list is called an array, and understanding it is the difference between being confused by n8n and actually controlling it.

One array in, the same node run once per item, automatically

This is why an n8n execution sometimes shows "3 items" flowing through a step instead of "1" — it isn't a bug, it's exactly one item per order in that array. Zapier and Make have their own version of this (Loops, and Iterators), but the underlying idea is identical everywhere: when the data coming in is a list, the automation quietly repeats the same step once for every entry in it.

Kung minsan, hindi lang isang bagay ang ibinabalik sa'yo — grupo na ng mga bagay, parang listahan. Tinatawag itong array. Kung tatlong order ang dumating, gagana ang node mo ng tatlong beses — isang beses para sa bawat isa, kusa na mismo, walang kailangang gawin pa.

What "Every 5 Minutes" Actually Means STEP 9

Back in Step 4 you saw that polling means checking on a timer instead of waiting for a webhook. In n8n, Zapier, and Make that timer has a name — the Schedule Trigger — and under the hood it's almost always described using a tiny five-part code called cron. It looks cryptic for about five minutes, and then it never looks cryptic again.

Five slots, left to right: minute, hour, day of month, month, day of week — a star just means "any"

Think of it like setting several alarms on your phone instead of one: a star in a slot means "any value here is fine," and a number pins that slot down to something specific. Most tools give you a friendly dropdown so you'll rarely type cron by hand — but now, when you see one of these five-part codes sitting in a Schedule node, you can read it instead of just trusting it.

Ang cron ay parang pagseset ng maraming alarm sa cellphone mo. Sa halip na isang alarm lang, pwede kang gumawa ng schedule tulad ng "tuwing ika-siyam ng umaga" o "bawat limang minuto" — at awtomatiko na itong gagana nang wala ka nang gagawin pa.

Retrying Without Hammering the Door STEP 10

Back in Step 7 you met status code 429 — Too Many Requests. Knowing what it means is half the battle; the other half is knowing what a well-built automation actually does about it. The answer is a pattern called exponential backoff, and it's simpler than the name suggests.

Fail, wait a little, fail, wait longer, fail, wait longer still, succeed
It's exactly like knocking on a friend's door. If nobody answers right away, you don't hammer the door fifty times a second — you wait a moment, knock again, wait a bit longer, and knock again. An automation calling a flaky or overloaded API should behave the same way: retry, but let the gap between attempts grow each time instead of retrying instantly forever.

This is exactly what "Retry on Fail" means when you see it on an n8n node, what Zapier is doing automatically behind the scenes on certain errors, and what a Make error handler's "Retry" option controls. Different labels, same idea you now already understand.

Kung minsan, hindi agad sumasagot ang ibang app — busy sila o marami silang tinatanggap na request. Sa halip na paulit-ulit mong kulitin agad, maghihintay ka muna nang kaunti, tapos susubukan ulit — parang kumakatok ka lang sa pinto, hindi basta-bastang binabayo.

When One Page Isn't Enough STEP 11

Ask an API for "all contacts" and if there are 50,000 of them, it almost never hands you all 50,000 at once. Instead it gives you a page — usually 20 to 100 records — plus a small breadcrumb telling you how to ask for the next batch. That breadcrumb goes by a few names (a cursor, a page token, a "next" URL) but it always does the same job.

A cursor, page token, or "next" URL — three names for the same breadcrumb
It's like asking a librarian for every book on a topic. She doesn't hand you the whole shelf at once — she gives you the first stack of 20 and a ticket number. You hand back that ticket for the next stack, and keep going until she tells you there's nothing left.
Kapag napakarami ng datos, hindi ibinibigay lahat agad — pinapahati muna sa mga pahina (pages). Kukunin mo muna ang unang pahina, tapos may senyales kang matatanggap (cursor o next page token) kung paano kunin ang susunod, hanggang sa maubos na ang lahat.
Many HTTP/API nodes in n8n and Zapier have a built-in "Auto-Pagination" or "Return All" option — turn that on and the tool loops through every page for you, instead of you building that loop by hand.

Not Doing the Same Thing Twice STEP 12

Networks hiccup. A webhook can fire twice for the exact same event, or the retry logic you learned in Step 10 can re-run a step whose first attempt actually succeeded but whose confirmation got lost along the way. Without protection, that means two emails, two invoices, or a customer charged twice for one real event. Making a workflow idempotent means it produces the same end result no matter how many times the same event shows up.

One extra check turns a dangerous duplicate into a harmless no-op
It's like getting the same text message delivered twice because your phone lost signal for a second. You don't reply to it twice — you recognize you've already answered this exact message and just let the repeat sit there.
Minsan, dalawang beses dumarating ang parehong trigger dahil sa glitch o retry. Ang idempotency ay pagsusuri muna kung nagawa mo na ba ito dati — kung oo, huwag mo nang ulitin. Kaya may check muna bago gumawa ng action, para hindi ka makapagpadala ng dalawang beses na email o resibo.
The usual fix is simple: before acting, look up whether you've already processed that exact ID (a spreadsheet lookup, a database record, or a "seen it" tag) and only continue if it's new.
Skipping this check is harmless for a duplicate Slack ping, but genuinely costly for anything involving money or a one-time action — a payment charged twice, a contract sent twice. Any workflow touching payments or contracts needs an idempotency check, not just a nice-to-have.

Filters, Conditions & Branching STEP 13

Every workflow eventually needs to make a decision: should this step even run, and if there's more than one thing it could do next, which path should the data take? Both questions come down to the same building block — a condition, which is really just a yes/no question about your data.

One yes/no question, two different destinations for the exact same lead

Underneath, every condition is built from a small vocabulary of comparisons: equals, does not equal, greater than, less than, contains, and is empty. Stack more than one together and you choose how they combine — AND means every single one must be true ("budget over $5,000 AND country is US"), while OR means just one of them needs to be ("urgent is yes OR budget over $10,000"). Mix those up and you'll either block leads that should have passed, or let everything through unfiltered.

A single condition is like a bouncer checking ID at one door — pass, and you're in; fail, and you're turned away, full stop. Branching is different: it's a fork in the road with several destinations, and each path is a real option, not a dead end.
Ang condition ay parang tanong na oo-o-hindi tungkol sa datos mo. Kung tama ang sagot, tumutuloy ang workflow; kung mali, humihinto o pumupunta sa ibang daan. Ang AND ay kailangang lahat totoo; ang OR naman, isa lang sa kanila sapat na.
n8n calls this the IF node (two paths) or Switch node (several paths). Zapier calls it a Filter (stop or continue) or Paths (branch). Make calls it a Router. Different names, same yes/no question underneath.

Sample lead: { budget: 8000, country: "US", urgent: false }. Build a condition and test it against that lead.

Putting All the Pieces Together STEP 14

Every automation you'll ever build, no matter how advanced it looks, is really just a longer version of the same four moves: something happens (a trigger — often a webhook), you go ask for more detail if you need it (a GET request), you reshape the data into the right shape (processing), and you tell another app to do something with it (a POST, PUT, or DELETE). Once you can spot those four moves inside any workflow, nothing in n8n, Zapier, or Make will look intimidating again.

This exact pattern is hiding inside almost every workflow you'll ever look at

Go back and look at the "Real Workflow Example" boxes in the n8n, Zapier, Make, and GHL lessons — every single one of them is this same four-move pattern, just with different app names filled in. Wrap the credential that proves who's asking, the status code that tells you whether it worked, the array that shows up whenever there's more than one result, the cursor that carries you across pages of results, the schedule that decides when it all starts, the patient retry that keeps it running when something hiccups, the quiet check that stops a retry from becoming a duplicate, and the yes/no question that sends each record down the right path — and you now have every idea you need to read any node in any tool without guessing. The Capstone Project tab puts every one of these pieces together in one real, buildable workflow.

Kung susumahin: may nangyari (trigger), humingi ka ng detalye (GET), inayos mo ang datos (processing), tapos sinabihan mo ang ibang app na gumawa ng something (POST, PUT, o DELETE). Apat na hakbang lang — paulit-ulit lang ito sa bawat automation na gagawin mo, kahit gaano pa ito kacomplicated.

Headers & Payload — The Anatomy of a Request BONUS

Every request you've learned about — GET, POST, whatever the verb — is actually made of three parts. The URL says which endpoint. The Headers carry metadata about the request itself — "this is JSON," "here's my API key." The Body (also called the Payload) is the actual JSON data being sent, and it usually only shows up on POST and PUT — a GET request is just asking for something, so there's nothing to include inside.

One request, three parts — this is what's really sitting inside every HTTP Request node
It's a shipped package: the URL is the delivery address, the Headers are the shipping label details (fragile, this-side-up, return address), and the Payload is what's actually inside the box. A GET request is like an empty envelope with just a request written on the outside — there's no package to open.
Bawat request na natutunan mo — GET, POST, kahit ano pa — ay binubuo ng tatlong bahagi: ang URL (saang endpoint), ang Headers (impormasyon tungkol sa request mismo, gaya ng "JSON ito" o "narito ang API key ko"), at ang Body/Payload (ang aktwal na JSON na datos na ipinapadala, nasa POST/PUT lang karaniwan). Ang GET naman ay parang walang lamang sobre — humihingi ka lang, walang ipinapadalang laman.
The most common header you'll configure by hand is Authorization — this is literally where your API key or OAuth token rides along on every single request. Content-Type: application/json is the second most common — it tells the server "what I'm sending you is JSON, please parse it that way."

What is n8n?

n8n (pronounced "n-eight-n") is an open-source workflow automation tool. It's like a visual programming language where you drag and drop to create automations.
n8n is like a visual LEGO builder for automation. Traditional programming means building from raw materials; n8n means snapping pre-made LEGO blocks together. You don't need to code — you just connect blocks!

Nodes

A Node is a single block/action in n8n. Each node does ONE specific thing.
  • Trigger Node: Starts the workflow (e.g., Webhook, Email, Schedule)
  • Action Node: Does something (e.g., Send Email, Create Row, Call API)
  • Logic Node: Makes decisions (e.g., IF/ELSE)
A node is like a single Lego block — it does one job by itself, but the real workflow appears once you snap several of them together in order.
Ang Node ay parang isang piraso ng Lego — iisa lang ang ginagawa nito, pero kapag pinagsama-sama mo ang maraming node, doon lumalabas ang buong workflow.

Resource & Operation — Every Node's DNA

Open almost any action node and, before anything else, you'll see two dropdowns: Resource (the THING you're working with) and Operation (the ACTION to perform on it).
Resource + Operation forms a sentence: Resource is the noun, Operation is the verb. "Resource: File" + "Operation: Write File to Disk" = "Write a file to disk." "Resource: DONKI Solar Flare" + "Operation: Get" = "Get a solar flare."
  • Credential: WHICH account n8n uses to connect (e.g., "NASA account", "Gmail account")
  • Resource: WHAT type of thing inside that app (File, Message, Contact, Solar Flare Data...)
  • Operation: WHAT to do to it (Get, Create, Write File to Disk, Send...)
  • Additional Fields: Extra settings specific to that operation (Start Date, File Path...)
Change the Resource first — n8n automatically updates the Operation list to only show what's actually possible for that resource.
Ang Resource at Operation ay parang pangngalan at pandiwa sa isang pangungusap — sinasabi ng Resource kung ANO ang bagay, at ng Operation kung ANO ang gagawin dito. Palitan mo lang ang Resource, awtomatikong nagbabago rin ang listahan ng posibleng Operation.

Connections

Connections are the lines between nodes. They pass data from one node to the next.
Think of connections like pipes in a factory: water (data) flows from one machine to the next, each machine processes it, and the output goes to the next machine.
Ang mga Connection ay parang tubo sa pabrika — dumadaloy ang datos (parang tubig) mula sa isang makina papunta sa susunod, at bawat makina ay may sariling ginagawa dito bago ito ipasa pa.

Expressions & Variables

Expressions let you use dynamic data. Instead of "Hello John", use "Hello {{ $node.PreviousNode.data.firstName }}"
{{ $node.TriggerNode.json.email }} {{ $node.GetUser.data.name | uppercase }} {{ Date.now() }}
An expression is like a fill-in-the-blank form letter — instead of writing "Hello John" by hand every time, you write "Hello {name}" once, and the right name drops in automatically for every single person.
Ang Expression ay parang liham na may blangkong espasyo — sa halip na isulat mo ang pangalan ng bawat tao nang paulit-ulit, isang beses mo lang isusulat ang "Hello {name}", at awtomatiko nang mapapalitan ito ng tamang pangalan sa bawat pagkakataon.

Credentials

Credentials are how you connect n8n to your apps (Gmail, Slack, etc.). You authenticate once, use forever.

A credential is like a keycard you badge in with once at the front desk — after that, every door in the building recognizes you without asking again.
Ang Credential ay parang keycard na iisang beses mo lang ipapakita sa reception — pagkatapos noon, kahit saang pinto ka pumunta sa loob, kinikilala ka na nito nang hindi na kailangang magpakita ulit.

Execute Step — Test One Node at a Time

The Execute step button runs ONLY the node you're looking at, right now, and shows you the real INPUT and OUTPUT immediately — no need to run the whole workflow just to check one node.
  • The orange/green "Execute step" button runs just this node
  • The OUTPUT panel shows the exact data (or error) that node produced
  • Test each node as you build it — don't wait until the end to discover something's broken
It's like tasting the sauce while it's still on the stove instead of waiting until the whole dish is plated — you catch a problem exactly where it happened, not three steps later.
Parang tinitikman mo ang sarsa habang niluluto pa lang, sa halip na maghintay hanggang matapos ang buong ulam — agad mong nahuhuli ang problema sa mismong pinanggalingan nito, hindi na kailangang maghanap pa pagkatapos ng lahat.

Binary Data — Handling Files

Text and numbers travel as regular JSON. Actual files (images, videos, PDFs) travel as binary data — a separate field (usually named "data") carrying the file itself plus metadata: File Name, File Extension, Mime Type, and File Size.
When a node asks for an "Input Binary Field", it wants the NAME of that field (almost always data) — not the file itself. Get the name wrong and the node can't find the file.
Think of JSON as a filled-out order form, and binary data as the actual package being shipped alongside it — the form describes the package, but the package itself travels separately.
Isipin mong ang JSON ay parang resibo, at ang binary data naman ay ang aktwal na pakete na kasama nitong ipinapadala — inilalarawan ng resibo ang laman, pero ang pakete mismo ang aktwal na dumadaan.

Merge Node — Bringing Branches Back Together

After an IF or Switch node splits your workflow into separate paths (see the Filters & Branching lesson in Web Basics), a Merge node is how you bring those paths back into one, so a later step — like logging to a spreadsheet — runs no matter which branch a given item took.

It's like keeping one master recipe for "how we make dough" instead of retyping the same instructions inside your pizza recipe, your bread recipe, and your pasta recipe — write it once, call it from everywhere.
Sa halip na kopyahin ang parehong hakbang sa maraming workflow, gagawa ka ng isang "sub-workflow" na naglalaman ng paulit-ulit na proseso. Kapag kailangan mo ito, tatawagin mo na lang gamit ang Execute Workflow node — parang tumatawag ka sa isang taong eksperto sa isang gawain, sa halip na gawin mo lahat mag-isa.
Reach for a sub-workflow the moment you catch yourself copy-pasting the same 4-5 nodes into a second workflow — fix a bug in the sub-workflow once, and every workflow that calls it is fixed too.

Pinned Data — Stop Re-Triggering While You Build

Pinning freezes the output of a node — usually your trigger — so every node after it always sees that same sample data, even though the workflow isn't actually running. You can then build and test the rest of the workflow without needing a real webhook to fire every single time.
It's like working from a printed photo instead of asking someone to stand in front of you every time you want to sketch them — the photo (pinned data) never changes, so you can practice as many times as you need.
Sa halip na paulit-ulit mong i-trigger ang totoong webhook habang ginagawa mo pa lang ang workflow, pwede mong "i-freeze" ang datos ng isang node. Kahit hindi na tumatakbo ang tunay na trigger, gagamitin pa rin ng ibang node ang naka-pin na sample data — mas mabilis at hindi ka aabalahin sa bawat pagsubok.
Unpin before you go live — pinned data is a building tool, not something you want left active on a production workflow.

Wait Node — Pausing Until Something Happens

The Wait node pauses a workflow until something happens — a fixed amount of time, a specific date, or even until an external system calls back a special webhook URL the node itself generates. Nothing the workflow already knows gets lost while it waits.
It's like putting a letter in a mailbox with "hold for pickup" instructions — the letter doesn't disappear, it just sits there safely until the right person shows up to continue the process.
Ang Wait node ay nagpapahinto muna sa workflow — maaaring hintayin ang oras, petsa, o kahit sagot mula sa ibang system gamit ang espesyal na webhook link nito. Hindi nawawala ang datos habang naghihintay; nakatago lang ito hanggang sa tamang sandali para magpatuloy.
The webhook-resume option is the powerful part — you can pause a workflow waiting for a human to click "Approve" in an email, then have that click resume the exact same run.

An Error Trigger Workflow is a separate workflow that n8n automatically runs whenever any other workflow connected to it fails — instead of scattering error-handling logic inside every single workflow, you build it once, centrally.
It's a single fire alarm wired to every room in a building, rather than installing a separate alarm system in each room — one failure, anywhere, rings the same bell.
Sa halip na maglagay ng hiwalay na error-handling sa bawat workflow, gagawa ka ng isang "Error Workflow" na awtomatikong tatakbo kapag may nabigo — kahit saang workflow pa ito manggaling. Isang beses mo lang itong gagawin, pero saklaw na nito lahat.

It's a light switch on the wall instead of rewiring the ceiling fixture every time you want a different bulb — flip the switch (change the variable) and everything downstream responds, no rewiring required.
Sa halip na baguhin ang loob ng workflow tuwing magpapalit ka ng setting — halimbawa, mula test papuntang totoong server — isang beses mo lang ise-set ang Environment Variable. Kapag binago mo ito, awtomatiko nang sumusunod ang buong workflow nang hindi mo kailangang buksan at ayusin ang bawat node.
Keep separate variables for development and production API keys — this is exactly what stops a test run from accidentally emailing real customers.

It's like saving a document as a file you can email to a coworker, instead of them having to rebuild your entire spreadsheet from scratch by watching over your shoulder.
Bawat workflow sa n8n ay pwedeng i-save bilang isang JSON file — parang pag-export ng dokumento. Puwede mo itong ipadala sa ibang tao o gamitin sa ibang account, hindi na kailangang gawin ulit mula sa umpisa.

How to Read Any Error Panel

When a node fails, n8n shows the Error code (a short technical label), the Full message (human-readable detail, usually with the exact path or field), and which node failed. "Other info" hides the full stack trace for deep debugging.
  • ENOENT = "Error, NO ENTry" — the file or folder doesn't exist at that path
  • Read the Full message first — it usually names the exact path or field that's wrong
  • Click Execute step on the PREVIOUS node to confirm it actually produced what this node expected
  • A typo in a file path, or an Input Binary Field name that doesn't match, is the #1 cause of "file not found" errors

If Zapier is a straight line of dominoes, Make is a whole domino layout with forks in the road — one trigger can branch into several paths at once, and you watch data move visually along the lines as you build.
Make ay parang Zapier pero mas visual at mas malakas. Makikita mo talaga yung buong daan ng data — saan ito pumupunta, saan nagbabranch. Mas mura rin siya kung marami kang ginagawa.
Make prices by Operations (each individual action a module performs), not "tasks" like Zapier — and its free tier (1,000 ops/month) is more generous than Zapier's.

Make Core Concepts INTERMEDIATE

Scenarios

A Scenario is Make's term for a workflow/automation — equivalent to a Zapier "Zap" or an n8n "Workflow".
  • Built visually on a canvas, module by module, in a circular layout
  • Can branch into multiple paths from one trigger
  • Runs on a schedule or instantly — your choice
A Scenario is Make's recipe card — the same idea as a Zap in Zapier or a Workflow in n8n, just drawn on a round canvas instead of a straight line.
Ang Scenario ay ang recipe card ng Make — kaparehong ideya ng Zap sa Zapier o Workflow sa n8n, pero nakaguhit sa bilog na canvas sa halip na tuwid na linya.

Modules

A Module is Make's version of a node/step — one action inside an app (the same idea as n8n's "Node").
Module ay parang isang bilog na kahon sa Make canvas — bawat bilog, isang aksyon. Ikonekta mo yung mga bilog sa isa't isa, tapos may workflow ka na.
A module is Make's version of a single Lego block — one small job by itself, and the scenario comes alive once you snap several of them together in a chain.

Bundles & Operations

A Bundle is one packet of data flowing between modules. An Operation is counted every time a module processes one bundle — that's what you're billed on.
If a module processes 10 leads in one run, that's 10 operations for that module, not 1. Watch modules that loop over lists — they rack up operations fast.
Ang Bundle ay isang pakete ng datos na dumadaloy sa pagitan ng mga module. Ang Operation naman ay binibilang tuwing may isang module na nagpo-proseso ng isang bundle — dito ka babayad, kaya mag-ingat sa mga module na umuulit sa listahan.

Routers & Filters

A Router splits one path into multiple branches. Each branch can have its own Filter deciding whether data continues down that specific path.
  • Route A: IF order > $100 → send VIP email
  • Route B: IF order ≤ $100 → send standard email
  • Both routes run from the same trigger, side by side
A Router at a fork in the road is like a train switch — the same track splits into several, and each train (bundle) only goes down the track whose conditions it actually matches.
Ang Router sa sangang-daan ay parang switch ng tren — nagkakahati ang isang riles sa marami, at ang bawat tren (bundle) ay dadaan lamang sa rilis na tumutugma sa kanyang kundisyon.

Advanced Make ADVANCED

Iterators & Aggregators

An Iterator splits an array into individual bundles so you can process each one separately. An Aggregator does the reverse — collecting many bundles back into one array or file.
  • Iterator: "Here are 20 orders" → process one at a time
  • Aggregator: 20 processed orders → 1 combined report
An Iterator is like dealing a deck of cards one at a time to each player; an Aggregator is collecting everyone's cards back into one deck at the end of the round.
Ang Iterator ay parang pamimigay ng baraha nang isa-isa sa bawat manlalaro; ang Aggregator naman ay ang muling pagsasama-sama ng lahat ng baraha pabalik sa isang mazo pagkatapos ng laro.

Error Handlers

Attach an error handler directly to any module to control exactly what happens if it fails.
  • Resume: use a fallback value and continue
  • Retry: try the module again automatically
  • Break: pause the scenario and store it for later
  • Ignore/Commit: skip the error and keep going
It's a safety net under a tightrope walker — most walks finish fine, but when a step goes wrong, the net decides exactly what happens next instead of a hard fall.
Parang lambat sa ilalim ng manlalakad sa lubid — kadalasan ay tapos nang maayos ang paglakad, pero kapag may pagkakamali, ang lambat ang magpapasya kung ano ang susunod na mangyayari sa halip na basta na lang mahulog.

HTTP & Webhooks Modules

Just like n8n and Zapier, Make can call any API directly or receive a webhook to trigger a scenario instantly.
Kapareho ito ng natutunan mo na sa Web Basics at sa ibang tool — direktang tumatawag sa alinmang API, o tumatanggap ng webhook para agad na simulan ang scenario.
It's the same universal-adapter idea from the API Requests lesson — a direct call for apps without a native Make connector, and a private mailbox address for apps to push data into instantly.

Responding to a Webhook

Every lesson so far treated a webhook as one-directional — it fires, your workflow reacts. But the app that sent the webhook is often waiting for a response, not just silence. Make's "Webhook Response" module lets a scenario send a real reply back — a status code, a message, even a redirect — before the caller's own request times out.
It's the difference between texting someone who never replies (they're left wondering if it even sent) and texting someone who at least sends back a thumbs-up — the sender knows their message actually landed.
Kadalasan, hindi lang basta nag-a-abang ang nagpadala ng webhook — gusto rin nilang malaman kung natanggap at na-proseso ang kanilang hiling. Ang Webhook Response ay ang pagbibigay ng sagot pabalik, parang pagsagot sa text imbes na iwanang naka-"seen" lang.
This matters most for anything a person is actively waiting on — a payment confirmation page, a chatbot reply, a form that shows "success!" the instant it submits. Without a response module, the caller just sees the request hang.

Scenario History — Rerunning What Failed

Every time a scenario runs, Make keeps a full execution history — the exact data that went in and out of every module. When one run fails, you can open that specific execution and click Rerun instead of guessing what went wrong or resubmitting the original trigger.
It's like a security camera recording for every single run — instead of trying to remember what happened, you rewind the tape and watch the exact moment things went sideways.
Iniimbak ng Make ang detalye ng bawat pagtakbo ng scenario — kung ano ang pumasok at lumabas sa bawat module. Kapag may nabigo, buksan mo lang ang execution history para makita mo mismo kung saan ito na-stuck, tapos i-rerun mo na lang nang direkta, hindi na kailangang ulitin mula simula.
Check execution history before assuming a scenario is broken — often it's one bad record in one run, not the whole design.

Text Parser — Pulling Structure Out of Messy Text

The Text Parser module uses patterns (regular expressions, or "regex") to pull specific pieces out of unstructured text — like grabbing just the order number out of a full email body, or the phone number out of a paragraph.
It's a highlighter with very specific instructions: "highlight anything that looks like a phone number" — it scans the whole page and pulls out only the pieces matching that shape.
Minsan, hindi malinis ang datos na dumarating — halong-halo ang impormasyon sa isang malaking text. Ang Text Parser ay parang naghahanap ng tiyak na hugis sa loob ng gulong iyon, katulad ng email address o numero ng order, at kinukuha lang ang eksaktong bahaging kailangan mo.
You don't need to be a regex expert — Make ships common presets (email, URL, phone number) so you can often skip writing the pattern yourself.

Sleep Module — A Speed Bump on Purpose

The Sleep module pauses a scenario for a set number of seconds before the next module runs — Make's equivalent of Zapier's Delay step or n8n's Wait node.
It's a speed bump on purpose — you're not stopping the car, just making it slow down for a moment before continuing down the road.
Ang Sleep module ay nagpapahinto muna nang ilang segundo bago tumuloy sa susunod na module — kapareho ng Delay sa Zapier o Wait sa n8n, iba't ibang pangalan lang, parehong ideya.
Reach for Sleep when an API needs a moment to finish processing something on their end before your very next step asks for the result.

Scenario Scheduling — Cron With a Calendar Picker

Beyond a simple "every X minutes," Make's scheduling settings let a scenario run at specific times of day, on chosen days of the week, or immediately as data arrives — all without writing a cron expression by hand.
It's the same idea as the cron lesson from Web Basics, but presented as a friendly calendar picker instead of a five-part code — same underlying schedule, easier to read.
Katulad ng cron na natutunan mo sa Web Basics, pero sa Make, hindi mo na kailangang mag-type ng code — pipiliin mo na lang sa kalendaryo kung anong oras o araw dapat tumakbo ang scenario mo.
Use "immediately" scheduling only for scenarios triggered by a real webhook — for anything polling an API, a real interval saves you from wasted operations.

Set Variable — A Sticky Note for Later

A Set Variable module stores a value in the middle of a scenario's run, so a later module — possibly several steps downstream — can reuse it without needing to reference the original source again.
It's a sticky note you leave for your future self earlier in the day — jot the number down now, and grab it later without going back to recalculate it.
Ang Set Variable ay parang paglalagay ng tandang papel sa gitna ng proseso — isinusulat mo ang isang value ngayon, tapos kukunin mo na lang ito sa susunod na module kahit ilang hakbang pa ang layo, hindi na kailangang balikan ang pinagmulan.
Reach for a variable when the same calculated value (like a formatted full name) is needed in three different modules later in the scenario — set it once instead of recalculating it three times.

Blueprint — Exporting a Whole Scenario

A Blueprint is Make's exported version of a scenario — a single file capturing every module and connection — that can be imported into another account or shared with someone else to recreate the exact same scenario.
It's the same idea as a blueprint for a house: hand it to a different builder, and they can construct an identical structure without you standing there explaining every wall.
Ang Blueprint ay ang na-export na bersyon ng iyong buong scenario — isang file na naglalaman ng lahat ng module at koneksyon. Maibabahagi mo ito sa iba o ma-import sa ibang account, at magkakaroon sila ng eksaktong kaparehong scenario nang hindi na kailangang gawin ulit mula simula.
Export a Blueprint before making a risky change to a working scenario — if the change breaks something, importing the old Blueprint instantly restores exactly what worked before.

Data Stores

Make includes a built-in mini-database (Data Store) so you can save and look up records without connecting a separate spreadsheet or database.
It's a small notebook Make keeps just for your scenarios — jot something down in one run, and read it back in a completely different run later, without needing a separate spreadsheet or database app.
Parang maliit na notebook na iniingatan ni Make para sa mga scenario mo — pwede kang magsulat dito sa isang pagtakbo, at basahin ulit ito sa ibang pagkakataon, nang hindi na kailangan pa ng hiwalay na spreadsheet o database.

  • Cache responses to avoid redundant calls

4. Scalability Patterns

Design workflows that can handle growing data without breaking.
  • Use batch processing instead of loop-by-loop
  • Archive old data to keep processing fast
  • Monitor execution times
  • Optimize queries and filters
  • Use caching layers

5. Testing & Debugging Strategies

How to test automations before going live.
  • Test with real data first (not production)
  • Create test accounts/environments
  • Check execution logs after each run
  • Monitor first 10 runs manually
  • Set up monitoring & alerts

6. Building for Scale (1000s of users)

When your automation needs to handle massive volume.
  • Use queuing systems (not real-time processing)
  • Distribute load across multiple workflows
  • Use databases instead of files
  • Monitor costs (tasks, API calls, storage)
  • Implement rate limiting and throttling

Frequently Asked Questions & Pro Tips REFERENCE

What if I don't know how to code? Can I still automate?

YES! Absolutely. Zapier and GHL require ZERO coding. n8n is visual BUT has a "Code" node if you need it. Most users never touch code. Start with Zapier or GHL.

How much can I automate? Are there limits?

Limits exist but are high: Zapier is limited by tasks (cost-based), GHL is unlimited within your plan, and n8n is unlimited if self-hosted. Most businesses never hit limits. Start small, scale up.

Is automation secure? What about data privacy?

Modern platforms are VERY secure: encrypted connections (HTTPS/SSL), credentials stored securely (not in logs), compliance with GDPR/CCPA, and regular security audits.

Pro tip: Never hardcode sensitive data. Use encrypted credential storage.

What if a workflow breaks? Will my business stop?

Build resilience from the start: error handling (try/catch), retry logic (automatic retries), monitoring & alerts (know when it fails), fallback actions, and always keep a manual override.

How do I know if automation will save me money?

Do the math:
Manual time cost = (Hours/month × Hourly rate)
Automation cost = Tool subscription + Setup time

Example: 10 hours/month × $25/hr = $250/month. Zapier costs $50/month = $200/month saved!

ROI is usually positive within 1-2 months.

Should I use Zapier, n8n, Make, or GHL? Which is best?

Depends on your needs:

Use Zapier if: You want quick setup, simple workflows, non-technical
Use Make if: You want more power/branching than Zapier without writing code, and cheaper pricing at volume
Use n8n if: You need complex logic, self-hosted, developer-friendly
Use GHL if: You're an agency or need complete CRM + automation

Or use the interactive tool picker in the Advanced Mastery tab, or a COMBINATION of them all!

How do I test automations safely?

Testing best practices:
  • Create test accounts/emails (test@yourdomain.com)
  • Use staging environments when possible
  • Run workflows manually first (not on schedule)
  • Check execution logs thoroughly
  • Verify data in destination app
  • Only automate after 5+ successful manual tests

How do I charge clients for automation setup?

What's the difference between a Zap and a Workflow?

Same thing, different names:
- Zapier calls it a "Zap"
- n8n calls it a "Workflow"
- GHL calls it an "Automation"

All mean: A sequence of actions triggered by an event.
